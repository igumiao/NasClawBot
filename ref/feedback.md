# Phase 1 Feedback: LLM Usage Strategy Drift

## Summary

Current Phase 1 is runnable as a heuristic MVP, but it does not match the original Phase 1 design around LLM usage.

The main issue is not M-Team or qBittorrent connectivity. The main issue is that the current workflow does not actually use a real large language model for natural-language understanding, feedback parsing, or explanation generation.

As a result, the product currently behaves more like:

- a rule-based search shell
- plus LangGraph orchestration
- plus real adapter execution

rather than the intended Agent flow described in the design.

## Main Gaps Against the Original Design

### 1. No real LLM is used for natural-language constraint extraction

In `app/llm/client.py`, the workflow currently uses `LocalConstraintExtractor`, which is a heuristic stub rather than a model-backed extractor.

What it currently does:

- detects urgency from words like `tonight`, `quick`, `fast`, `今晚`
- detects rough `media_type` from words like `movie`, `film`, `电影`, `tv`, `剧`
- leaves most other fields unparsed

Most importantly:

- `query_text` is set to the full raw user message
- `title` is not extracted
- `year` is not extracted
- `preferred_resolution` is not extracted

This does not match the intended Phase 1 design where the LLM should convert natural language into structured constraints.

### 2. The search API is currently called with the full user sentence

In `app/api/chat_routes.py`, `AdapterSearchTool.__call__()` passes:

- `keyword=constraints.query_text`

And `constraints.query_text` is currently just the original user message.

Example:

User input:

`帮我找沙丘电影，今晚想看，优先下载快的版本`

Current search payload keyword:

`帮我找沙丘电影，今晚想看，优先下载快的版本`

That means the system is not searching for a parsed title like `沙丘` or `Dune`, but for the entire natural-language request.

This is the direct reason long natural-language requests often return:

- zero results
- or weakly related results

### 3. LangGraph defaults to the local heuristic extractor

In `app/workflow/graph.py`, `build_workflow()` defaults to:

- `LocalConstraintExtractor()`

And the current app wiring does not inject any real model-backed extractor.

This means the graph structure exists, but the intended LLM-powered understanding node is still only a stub.

So the current system has:

- LangGraph orchestration

but not:

- real LLM-based intent parsing

### 4. `reject_and_refine` does not perform structured feedback parsing

The original design expected confirmation-stage feedback such as:

- `不是电视剧，是电影`
- `我要 4K`
- `今晚就想看`

to be parsed into structured updates and merged into the current request constraints.

But in `app/workflow/graph.py`, `reject_and_refine` currently just does:

- rerun `run_chat()` with the new feedback text

This means:

- there is no dedicated confirmation feedback parser
- no merge of old constraints with new feedback
- no true human-in-the-loop refinement memory across turns

So the current behavior is closer to:

- "search again with a new sentence"

rather than:

- "update the previous plan with new structured constraints"

### 5. Recommendation explanation is not generated by an LLM

In `app/workflow/nodes.py`, the confirmation explanation is currently a fixed string:

- `This result ranked first based on deterministic relevance and availability rules.`

This does not match the original intended split:

- ranking core by rules
- ranking explanation by LLM

The first half is implemented.
The second half is not yet implemented.

### 6. The `app/llm/` layer is only a placeholder right now

The project structure already includes:

- `app/llm/client.py`
- `app/llm/prompts.py`

But these currently act as placeholders for future integration, not as an actual model-backed implementation.

Also, `app/config.py` does not currently expose model runtime settings such as:

- provider
- model name
- model API key
- model base URL

So from a runtime perspective, the app is not yet capable of calling a real LLM.

## Real User Impact

These implementation gaps already show up in realistic usage testing:

### Case A: Long natural-language request

Input:

`帮我找沙丘电影，今晚想看，优先下载快的版本`

Observed behavior:

- workflow returns `awaiting_confirmation`
- but candidate list is empty

Likely root cause:

- the full sentence is sent directly to the M-Team search API as `keyword`

### Case B: Short keyword request

Input:

`沙丘`

Observed behavior:

- candidates are returned
- but relevance is rough
- loosely related items can rank highly just because they contain `沙丘` in metadata

Likely root cause:

- weak title extraction
- no real semantic understanding
- ranking only has rule-based surface matching, not better structured interpretation

### Case C: Refine flow

Input:

- initial request
- then refine with `不要电视剧，只要电影，最好4K`

Observed behavior:

- the system reruns a new search from the refinement sentence itself
- it does not preserve and update previous structured constraints

Likely root cause:

- no structured feedback parsing node

## Recommended Fix Priority

### Priority 1: Implement the most basic semantic understanding only

Target:

- handle only the simplest natural-language patterns first, such as:
  - `我要看沙丘2`
  - `帮我下载沙丘2`
- use the LLM only to infer the single work title the user wants
- output only one primary keyword, not multiple fallback keywords
- prefer extracting a Chinese work title when possible, because current search behavior is more robust on that path

Suggested minimal structured output:

```json
{
  "title_keyword": "沙丘2",
  "intent": "search_and_prepare_download"
}
```

This should be treated as the first correction before adding broader semantic understanding.

### Priority 2: Stop using the full sentence as the search keyword

Target:

- search primarily using the inferred `title_keyword`
- do not pass the full natural-language sentence directly as the M-Team search keyword
- keep the first version narrow and stable rather than trying to interpret many attributes at once

### Priority 3: Defer advanced scene understanding until after title extraction is stable

These examples should be explicitly treated as later-stage work, not part of the first semantic understanding correction:

- `我要看沙丘 4k的 50g以下的`
- `我要看安多第二季的第4集`
- `我觉得安多很好看 全部下载下来`
- `今晚就要看安多`

The main reason to defer them is scope control. They introduce:

- attribute parsing
- season/episode parsing
- pack-vs-single decision logic
- more complicated search/filter/ranking behavior

These belong to a second stage of semantic understanding.

### Priority 4: Add structured confirmation feedback parsing after basic title extraction works

Target:

- revisit `reject_and_refine` after the first-stage title extraction is stable
- merge updated user feedback into the previous request state instead of treating every refine step as a brand-new sentence

### Priority 5: Generate explanations with an LLM later

Target:

- keep ranking deterministic
- generate explanation text dynamically only after search quality is no longer dominated by keyword extraction problems

## Bottom Line

Current Phase 1 should be understood as:

- a technically working MVP
- with real adapter integration
- but with incomplete LLM integration

The implementation currently falls short of the original Phase 1 design specifically in the areas of:

- natural-language understanding
- refinement feedback parsing
- explanation generation

The next high-value correction is not more adapter work.
It is to bring real LLM behavior into the search and refinement path so the system behaves like the intended Agent product.

## Keyword Sensitivity Testing (2026-04-26)

After the M-Team adapter behavior was aligned with real API observations, an additional round of search-only testing was run to measure keyword sensitivity.

This testing stayed in:

- `search`
- `confirmation payload generation`

and did **not** trigger real qB download submission.

### What was tested

Two paths were compared:

- current app path: `POST /chat`
- direct adapter path: `MTeamAdapter.search_torrents_by_keyword(...)`

The following keyword variants were tested:

- `沙丘`
- `dune`
- `沙丘2`
- `dune2`
- `沙丘 2`
- `dune 2`
- `dune-2`
- `Dune: Part Two`
- `沙丘：第二部`
- `dune part 2`
- `dune part two`
- `Dune II`
- `沙丘II`
- `沙丘第二部`

Natural-language full-sentence variants were also tested through the current app path:

- `帮我找沙丘2电影`
- `I want dune2 movie`
- `帮我找 dune 2 movie`
- `帮我找 Dune: Part Two`

### Main findings

#### 1. Some keyword forms are robust, but others are surprisingly fragile

Robust or mostly usable forms:

- `沙丘2`
- `Dune: Part Two`
- `沙丘：第二部`
- `dune part 2`
- `dune part two`
- `Dune II`
- `沙丘II`

Fragile forms:

- `dune2`
- `dune-2`
- `沙丘第二部`

Observed behavior:

- `dune2` and `dune-2` returned zero candidates on both the current app path and the direct adapter path.
- `沙丘第二部` also returned zero candidates.
- The same intent written as `dune 2`, `Dune: Part Two`, or `沙丘：第二部` returned usable candidates.

This suggests that the current M-Team search path is sensitive to token boundaries and punctuation, not just semantic meaning.

#### 2. Chinese and English variants behave differently

For sequel-oriented intent:

- `沙丘2` produced strong, targeted sequel results.
- `dune` and `dune 2` produced candidates, but were noisier and more likely to mix first-film, sequel, or related-franchise entries.

This means Chinese numbered titles currently behave more robustly than compact English variants such as `dune2`.

#### 3. Generic keyword forms produce noisy top candidates

For broad terms like:

- `沙丘`
- `dune`

the system often returns candidates that merely mention `沙丘` in metadata rather than being the intended film itself.

Examples included:

- unrelated titles mentioning `“沙丘”女神`
- `沙丘：预言` TV-related entries surfacing high in app results

This means the current ranking stack can still overvalue shallow surface matches.

#### 4. Natural-language full sentences remain a major failure mode

The following realistic user inputs all returned zero candidates through the current app path:

- `帮我找沙丘2电影`
- `I want dune2 movie`
- `帮我找 dune 2 movie`
- `帮我找 Dune: Part Two`

This confirms that the current workflow is still too dependent on using the full raw sentence as the search keyword.

So even when the underlying M-Team search can handle a short keyword like:

- `沙丘2`
- `Dune: Part Two`

the app path fails because it does not first extract a clean title keyword.

### Practical conclusion

Current search behavior should be understood as:

- acceptable for short, well-formed title keywords
- weak for compact English variants like `dune2`
- weak for some Chinese no-punctuation variants like `沙丘第二部`
- poor for natural-language full-sentence requests

### Recommended next improvements

Priority should be:

1. Add keyword normalization before search.

Suggested examples:

- `dune2 -> dune 2`
- `dune-2 -> dune 2`
- `沙丘第二部 -> 沙丘：第二部` or `沙丘2`

2. Extract title-like search terms before calling M-Team.

Do not send the full user sentence directly as:

- `constraints.query_text`

Instead, derive a short search keyword such as:

- `沙丘2`
- `Dune: Part Two`

3. Add fallback retries for fragile variants.

If the first keyword returns no results, try one or two normalized alternatives before giving up.

4. Tighten strong-relevance ranking.

Entries that only mention the target term incidentally should rank below entries whose core title actually matches the intended film.

### Bottom line from this test round

The adapter-level M-Team search is usable, but the current app-level search experience is still bottlenecked by:

- weak keyword extraction
- lack of keyword normalization
- insufficient strong-match preference in ranking

The next user-visible quality gain will come less from adapter work and more from:

- better query rewriting
- better title extraction
- better match quality control
